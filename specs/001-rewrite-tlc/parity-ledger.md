# TLC Feature Parity Ledger

Purpose: enumerate every legacy TLC capability we must preserve in the Rust rewrite, trace each to the existing surface area, and capture the current porting approach and risk posture.

Sources reviewed:
- CLI option listing generated in `tlatools/org.lamport.tlatools/src/tlc2/TLC.java` lines 1595–1760.
- Model configuration keywords in `tlatools/org.lamport.tlatools/src/tlc2/tool/impl/ModelConfig.java` lines 53–142.
- Coverage behavior documentation in `docs/module-coverage-statistics.md`.
- Engine package structure (`tlatools/org.lamport.tlatools/src/tlc2/tool/**`) for fairness, simulation, SpecTE, and checkpointing semantics.

Status legend:
- ✅ Covered in Rust plan/design.
- 🟡 Planned but needs deeper design detail.

## Config Loader Parity Notes

- **Source resolution**: `RunConfiguration` delegates to `ConfigSource::resolve(spec_source, cli_override)` which mirrors Java semantics. If the user omits `-config`, we probe (in order) the explicit archive payload (`/model/MC.cfg`), a sibling `${spec}.cfg` next to the primary module, and finally a monolithic `SPEC.tla` section marked with `----- CONFIG SPEC -----`. CLI `-config foo` accepts bare basenames (`foo`), explicit `.cfg` paths, or `.tla` monoliths; relative paths are interpreted against the launch CWD unless `--spec-root` (from the spec bundle flow) overrides it.
- **Parsing strategy**: A dedicated `config::parser` crate reuses the shared TLA+ lexer (same tokenization as SANY) so comments, Unicode escapes, and Toolbox-generated spacing stay legal. The recursive-descent parser follows `ModelConfig`’s grammar exactly: single- and multi-entry `CONSTANT(S)` blocks, `<-` expression overrides (stored as TLA AST strings), `=` literal assignments (numbers, strings, booleans, finite sets, or model values), module-scoped overrides via `<-[Mod]`, and module-specific constant lists via `=[Mod]`. During parsing we capture both typed data (for the engine) and a `raw_constants` list preserving the original text block for round-tripping back to UIs.
- **Keyword coverage**: All supported keywords (`SPECIFICATION`, `INIT`, `NEXT`, `SYMMETRY`, `CONSTRAINT(S)`, `ACTION_CONSTRAINT(S)`, `INVARIANT(S)`, `PROPERTY(IES)`, `ALIAS`, `VIEW`, `POSTCONDITION`, `CHECK_DEADLOCK`, etc.) map to strongly typed fields on `RunConfiguration`. Deprecated hooks (`_PERIODIC`, `_RL_REWARD`) still lex but surface as explicit “removed in TLC Rust” diagnostics that reference the migration doc.
- **Error fidelity**: Parse failures emit structured `ConfigError` values that carry the legacy `EC.CFG_*` message codes so `-tool` mode and the Toolbox continue to receive identical `MP` output. This includes duplicate keyword detection, missing identifiers, invalid constants, and bad boolean literals for `CHECK_DEADLOCK`. File resolution failures also re-use `EC.CFG_ERROR_READING_FILE` with the same wording.
- **Resolver integration**: The parser operates on streams from the unified resolver stack (`SpecSource`-aware filesystem/archive resolver + standard modules). This keeps toolbox library paths, temp directories (for jars), and override modules (`Foo.class` compiles) working without special cases.
- **Serialization**: Downstream writers (migration tooling, future `tlc bundle` command) consume a `ConfigDoc` surface that can regenerate `.cfg` files byte-for-byte when no semantic edits occur—matching Toolbox expectations for preserving user formatting and comments.

## Constant Value System Notes (`CONSTANT(S)`)

- **Literal grammar & model values**: `ModelConfig.parse()` only treats numbers, strings, booleans, and set enumerations as concrete literals; every other token becomes a `ModelValue` via `ModelValue.make` after resetting the table with `ModelValue.init()` (`tlatools/org.lamport.tlatools/src/tlc2/tool/impl/ModelConfig.java:309`, `tlatools/org.lamport.tlatools/src/tlc2/value/impl/ModelValue.java:42`). Rust must preserve typed-model-value semantics (prefix `_x_` tagging) and deterministic enumeration order so equality checks and fingerprinting remain stable.
- **Operator tables**: Multi-arity assignments such as `Op(1,2) = "a"` are folded into `OpRcdValue` instances by `SpecProcessor.makeConstantTable`, which materializes a finite lookup table used at runtime (`tlatools/org.lamport.tlatools/src/tlc2/tool/impl/SpecProcessor.java:2052`, `tlatools/org.lamport.tlatools/src/tlc2/value/impl/OpRcdValue.java:27`). The Rust evaluator needs the same record-backed operators, including arity validation and undefined-application diagnostics.
- **Overrides & module scoping**: `CONSTANT Foo <- Bar` rewrites `Foo` to reuse an existing definition pulled from the global `defns` map, while `Foo <-[Module] Baz` and `Foo =[Module] 42` target operators defined in specific modules (`tlatools/org.lamport.tlatools/src/tlc2/tool/impl/ModelConfig.java:329`, `tlatools/org.lamport.tlatools/src/tlc2/tool/impl/SpecProcessor.java:749`). The override pipeline prohibits chained substitutions, enforces arity equality, and raises `EC.TLC_CONFIG_ID_DOES_NOT_APPEAR_IN_SPEC` when the target is missing; every guard must be mirrored.
- **Assignment enforcement & diagnostics**: During elaboration each root constant must either receive a concrete value or appear in the override table—otherwise TLC halts with `EC.TLC_CONFIG_VALUE_NOT_ASSIGNED_TO_CONSTANT_PARAM` (`tlatools/org.lamport.tlatools/src/tlc2/tool/impl/SpecProcessor.java:524`). Additional failures (`EC.TLC_CONFIG_WRONG_SUBSTITUTION`, `_NUMBER_OF_ARGS`, `_SUBSTITUTION_NON_CONSTANT`) surface when users map to undeclared symbols, mismatch arity, or reference non-constant operators (`tlatools/org.lamport.tlatools/src/tlc2/tool/impl/SpecProcessor.java:786`, `tlatools/org.lamport.tlatools/src/tlc2/tool/impl/SpecProcessor.java:301`). The Rust implementation will emit the same codes so Toolbox integrations stay compatible.
- **Evaluation & caching**: When a config redefines an operator by value, TLC eagerly evaluates it in the constant context and, unless `SpecProcessor.aggressiveConstantCaching` is enabled, caches only constant expressions or explicit `TLCEval` wrappers (`tlatools/org.lamport.tlatools/src/tlc2/tool/impl/SpecProcessor.java:252`). We will mirror this opt-in caching toggle so users retain control over whether runtime randomness (e.g., `RandomElement`) is frozen during startup.
- **Raw serialization hooks**: `ModelConfig` retains the exact text for each `CONSTANT(S)` block (`tlatools/org.lamport.tlatools/src/tlc2/tool/impl/ModelConfig.java:177`, `tlatools/org.lamport.tlatools/src/tlc2/tool/impl/ModelConfig.java:498`), and export tooling replays it verbatim when emitting configs (`tlatools/org.lamport.tlatools/src/tlc2/output/AbstractSpecWriter.java:226`). Rust must maintain the same raw buffer to guarantee Toolbox round-trips preserve formatting and comments.
- **Regression coverage**: Legacy tests such as `tlatools/org.lamport.tlatools/test/tlc2/tool/TLCGetNamedUndefinedTest.java:46` and `tlatools/org.lamport.tlatools/test/tlc2/tool/suite/ETest7.java:43` assert the override error paths and undefined-substitution diagnostics. Add parity tests that: (1) reject missing assignments, (2) exercise module-scoped overrides, (3) confirm `ModelValue` typing, and (4) validate operator table evaluation produces identical traces.

## Alias Trace Mapping Notes

- **Config ingestion**: `ModelConfig.parse()` reads a single identifier after the `ALIAS` keyword (`tlatools/org.lamport.tlatools/src/tlc2/tool/impl/ModelConfig.java:249-262`). Duplicate keywords raise `EC.CFG_TWICE_KEYWORD`; a missing identifier surfaces `EC.CFG_MISSING_ID`. The value is stored verbatim so Toolbox round-tripping keeps the alias name unchanged.
- **Definition validation**: During spec elaboration `Spec.getAliasSpec()` looks up the identifier in the definition table and enforces that it is a zero-arity operator (`tlatools/org.lamport.tlatools/src/tlc2/tool/impl/Spec.java:223-256`). It reuses existing diagnostics—undefined names hit `EC.TLC_CONFIG_SPECIFIED_NOT_DEFINED`, constants trigger `EC.TLC_CONFIG_ID_MUST_NOT_BE_CONSTANT`, non-nullary operators raise `EC.TLC_CONFIG_ID_REQUIRES_NO_ARG`, and an empty alias is rejected with `EC.TLC_CONFIG_NO_STATE_TYPE`. Rust must mirror these failures so IDEs receiving `MP` output behave identically.
- **Evaluation pipeline**: `Tool.evalAlias` executes the alias expression for every state (and action) that will be printed or exported (`tlatools/org.lamport.tlatools/src/tlc2/tool/impl/Tool.java:1604-1687`). The evaluator seeds `IdThread` with the current state, passes both the current and successor `TLCState`, and treats a `null` result as “use the original state.” The Rust engine should surface the same API so components can call `eval_alias(current, successor)` without worrying about aliases being disabled.
- **Trace prefix access**: When TLCExt is extended, TLC binds `TLCExt!Trace` to the prefix of states about to be printed by wrapping the result in `AliasTLCStateInfo` (`tlatools/org.lamport.tlatools/src/tlc2/tool/impl/Tool.java:1634-1678`, `tlatools/org.lamport.tlatools/src/tlc2/tool/impl/AliasTLCStateInfo.java:32-62`). This lets alias definitions compute derived views (JSON, diffs, etc.) using the whole trace. The Rust port must provide the same TLCExt context binding so existing alias modules keep working.
- **Consumers**: Alias evaluation feeds every user-visible surface—error traces (`tlatools/org.lamport.tlatools/src/tlc2/tool/Worker.java:647-676`), invariant and implied-init diagnostics (`tlatools/org.lamport.tlatools/src/tlc2/tool/ModelChecker.java:1187-1202`, `tlatools/org.lamport.tlatools/src/tlc2/tool/Simulator.java:275-510`, `tlatools/org.lamport.tlatools/src/tlc2/tool/DFIDModelChecker.java:323-335`), simulation transcripts, and debugger/liveness reporting. We must retain these call sites so alias-based formatting continues to work regardless of exploration mode.
- **Failure shape**: Exceptions during alias evaluation are captured and added as an auxiliary record field `_ALIASEvalError` before returning the state (`tlatools/org.lamport.tlatools/src/tlc2/tool/impl/Tool.java:1617-1687`). Downstream printers display the augmented record rather than aborting the run. Rust should clone this behavior, including the error field name, so users see consistent diagnostics.
- **Toolbox serialization**: Toolbox-generated specs emit alias definitions via `AbstractSpecWriter.addAlias` (`tlatools/org.lamport.tlatools/src/tlc2/output/AbstractSpecWriter.java:512-536`). The rewrite must continue to accept those generated identifiers and preserve them when exporting models back to `.cfg` files.
- **Testing**: Plan regression coverage that (1) exercises both state-level and action-level aliases, (2) verifies TLCExt trace access, (3) ensures `_ALIASEvalError` propagation, and (4) checks that distributed and resume flows keep alias output stable. Golden traces for Toolbox/CLI output should be compared against legacy TLC to guard against formatting drift.

## Symmetry Reduction Parity Notes (`SYMMETRY`)

- **Config capture & lookup**: `ModelConfig.parse()` records the identifier following `SYMMETRY`, and `Tool.getSymmetryPerms()` resolves it from `unprocessedDefns`, enforcing the legacy diagnostics for undefined or ill-formed operators. The Rust loader will mirror this path so Toolbox round-trips keep the exact name and the same `EC.TLC_CONFIG_*` failures fire when the target is missing or not an operator.
- **Operator contract**: Legacy TLC expects the operator to evaluate to a finite set of function records that permute model values—typically produced by `TLC.Permutations` (`tlc2/module/TLC.java:286-360`). `Tool.getSymmetryPerms()` verifies the body is enumerable, that every element is a `FcnRcdValue`, and that each domain/range entry is a `ModelValue`, otherwise it throws `Assert.fail` with the historical message text. The Rust evaluator will reuse the shared `Value` system so non-model-value outputs still halt with identical errors.
- **Small-set diagnostics**: When any symmetry argument set is empty or singleton, TLC treats the definition as a no-op and prints `EC.TLC_SYMMETRY_SET_TOO_SMALL`, listing the offending set names (`Tool.java:3740-3785`). We will reproduce the same detection—including `ModelConfig.getOverridenSpecNameForConfigName` indirection—so users receive the familiar warning and the engine gracefully disables reduction in degenerate cases.
- **Permutation subgroup construction**: Valid symmetry sets are expanded with `MVPerms.permutationSubgroup`, which generates the closure of the provided permutations, deduplicates them via `Set`, and returns an `IMVPerm[]` array (`tlc2/value/impl/MVPerms.java:19-78`). Distributed runs may wrap intermediate values in `WorkerValue`; the helper unwraps them before building the subgroup. Rust will implement the same subgroup generation (including closure and `WorkerValue` unwrapping) to guarantee orbit membership matches Java for every worker.
- **State canonicalization & fingerprints**: `TLCStateMut.setTool()` caches the permutation array, and `TLCStateMut.fingerPrint()` enumerates every permutation, applying it to the state and keeping the lexicographically smallest valuation before hashing (`tlc2/tool/TLCStateMut.java:164-255`). The control flow (including the `NEXT_PERM` short-circuit and deep normalization) determines which representative is stored in the `FPSet`. Our Rust state representation will mirror this algorithm byte-for-byte so symmetrical states collapse to the same hash, view maps interact identically, and resume/checkpoint flows remain deterministic.
- **Liveness & coverage interactions**: When liveness checking is enabled, TLC prints `EC.TLC_FEATURE_UNSUPPORTED_LIVENESS_SYMMETRY` to warn about the soundness trade-off (`tlc2/tool/AbstractChecker.java:118-134`). Coverage collectors assume uniform exploration, which the comments in `CostModelCreator` flag as potentially wrong under symmetry reduction (`tlc2/tool/coverage/CostModelCreator.java:500-534`). The rewrite will keep both behaviors: emit the warning verbatim and document that coverage accuracy may drift when symmetry is active.
- **Persistence, distributed parity, and manifests**: Permutations are recomputed on startup from the config, so checkpoints only need the config payload; workers invoke `setTool()` locally to receive the same `IMVPerm[]`. The Rust manifest will therefore persist the symmetry identifier and ensure the distributed control plane replays it before exploring states, protecting fingerprint stability across resume/distributed boundaries.
- **Testing strategy**: Add regression tests that (1) confirm the warning for singleton symmetry sets, (2) compare Java and Rust canonical fingerprints across representative specs (e.g., mutual exclusion models with permuted process IDs), (3) verify liveness runs still flag `EC.TLC_FEATURE_UNSUPPORTED_LIVENESS_SYMMETRY`, and (4) exercise distributed/resume flows to ensure permutations survive `WorkerValue` transport. Include golden traces that demonstrate canonicalization does not change user-visible states or trace printing.

## Liveness Checking Parity Notes (`PROPERTY / PROPERTIES`)

- **Config ingestion & warnings**: `SpecProcessor.processConfigProps` resolves each name in `ModelConfig.getProperties()`, enforces zero-arity boolean operators, and reproduces the legacy diagnostics (`EC.TLC_CONFIG_SPECIFIED_NOT_DEFINED`, `_ID_REQUIRES_NO_ARG`, `_ID_HAS_VALUE`). The same pass keeps liveness heuristics intact: warning on missing `SPECIFICATION` when properties are present (`EC.TLC_CONFIG_NO_SPEC_BUT_PROPERTY`), warning when a behavior spec lacks fairness yet properties demand it (`EC.TLC_CONFIG_NO_FAIRNESS_BUT_LIVE_PROPERTY`), and catching tautological `S /\\ L => L` refinements (`EC.TLC_LIVE_FORMULA_AND_FAIRNESS_TAUTOLOGY`). Rust will emit the identical message catalog entries so Toolbox guidance survives the rewrite.
- **Fairness fusion & normalization**: `Liveness.processLiveness` fuses fairness obligations (`tool.getTemporals()` from `WF_/SF_` in the spec) with temporal properties (`tool.getImpliedTemporals()` from `PROPERTY` keywords). It lowers them to `OrderOfSolution` records that capture the tableau (`TBGraph`) for fairness conjuncts, the promises (`LNEven` / `LNAll`) that track `<>[]`/`[]<>` obligations, and per-branch state/action checks (`LiveExprNode`). Our Rust pipeline will reuse the same AST-to-live-expression lowering (`Liveness.astToLive`) so enabledness tests (`<<A>>_vars`), primed variables, and quantifiers behave identically.
- **Behavior & tableau graphs**: As the engine explores states, `ModelChecker.addInitState` and `addNextState` feed each `LiveCheck`. The checkers persist transitions into a disk-backed behavior graph (`DiskGraph`/`BEGraph`) plus optional tableau graph (`TableauDiskGraph`), keyed by fingerprints through `NodePtrTable` structures (stored under `-metadir`). Symmetry canonicalization happens before fingerprints are entered; when symmetry lands in the Rust port we must preserve the same integration point to avoid spuriously rejecting accepting cycles.
- **Safety shortcut & continuation semantics**: `LiveCheck.addNextState` evaluates each property’s state/action obligations as transitions appear; branches that are pure safety fail immediately with `EC.TLC_ACTION_PROPERTY_VIOLATED`/`EC.TLC_TEMPORAL_PROPERTY_VIOLATED`, while true liveness obligations enqueue for SCC analysis. Even with `-continue`, TLC halts on the first liveness counterexample. The Rust checker will keep this split so safety properties remain on-the-fly checks and continuation semantics match Java.
- **Runtime cadence & threading**: Incremental checking follows the Java rules: `LiveCheck.check` compares graph growth against `TLCGlobals.livenessThreshold` (~20 %) and honours `TLCGlobals.lnCheck` (`off|final|default`) before launching `LiveWorker` threads. Workers are bounded by `TLCGlobals.getNumWorkers` unless sequential mode is forced (`doSequentialLiveness()`), ensuring the new engine respects legacy defaults and `-workers 1` / `-debugger` interactions. Progress messages (`EC.TLC_CHECKING_TEMPORAL_PROPS*`) and timing output must remain byte-for-byte for scripting compatibility.
- **Violation handling & artifacts**: Accepting cycles raise `LiveCounterExampleException`, which carries the prefix, loop, fairness witnesses, and offending promises. TLC prints `TLC_TEMPORAL_PROPERTY_VIOLATED`, dumps the counterexample via `StatePrinter` (loop demarcated with `>>`), and—if DOT export is on—emits `_liveness.dot` snapshots through `DotLivenessStateWriter`. We will reproduce the same exception hierarchy, message codes, dot schema, and NDJSON/tool-mode payloads so IDE consumers and regression suites still recognize liveness failures.
- **Persistence & distributed parity**: Liveness graphs participate in checkpoints—`DiskGraph` and tableau tables serialize alongside reachability data, and resumes rebuild `OrderOfSolution` structures before exploration continues. Distributed TLC forwards liveness updates through `TLCMessage.LiveAdd`, expecting the server to merge them into its graph. The Rust runtime will record the same manifest entries, enforce flag parity (`-lncheck off` remains a server-side decision), and validate that resumes and remote workers rehydrate outstanding obligations before continuing.
- **Testing strategy**: Regression coverage must include (a) safety-only properties that trigger during successor insertion, (b) classic liveness specs with fairness (e.g., `OneBitClock`, `TwoPhase`), (c) refinement checks using implied temporals, (d) tautology and fairness-warning cases, (e) checkpoint/resume of in-progress liveness graphs, and (f) distributed runs that replay remote liveness updates. Counterexample traces and DOT files should be diffed against Java TLC to guarantee textual fidelity.

## Fingerprint Partition Parity Notes (`-fpbits`)

- **CLI parsing & validation**: `tlatools/org.lamport.tlatools/src/tlc2/TLC.java:1039-1066` accepts `-fpbits num`, requires an integer, and emits the legacy diagnostics `Error: An integer for fpbits required...` or `Error: Value in interval [0, 30] for fpbits required...` when validation fails (`FPSet.isValid` enforces `[0, MultiFPSet.MAX_FPBITS]`). The Rust CLI will mirror these checks, surface the same `EC.WRONG_COMMANDLINE_PARAMS_TLC` codes, and share the parser with distributed TLC (`tlc2/tool/distributed/TLCApp.java:430-450`).
- **Default & range semantics**: `FPSetConfiguration` defaults `fpBits` to 1, yielding two partitions out of the box. Setting `-fpbits 0` tells the Java pipeline to run a single `FPSet`; however, disk-backed implementations still require at least one partition and silently coerce 0→1 (`FPSetConfiguration.getFpBits`). Rust will preserve that behavior: on-heap implementations honor exactly the requested value, while disk/off-heap backends automatically elevate zero to one so their indexing invariants remain valid.
- **Partitioning mechanics**: When `fpBits > 0`, `FPSetFactory.getFPSet` returns a `MultiFPSet` that slices the fingerprint space into `2^fpBits` shards using the most-significant bits (`MultiFPSet` constructor and `getFPSet(fp)` in `tlatools/.../MultiFPSet.java:44-120`). Each shard wraps a child `FPSet` built via `MultiFPSetConfiguration`, which clones the parent config but divides memory by the shard count (`MultiFPSetConfiguration#getMemoryInBytes`). Rust’s storage layer will replicate this structure so high-cardinality models can scale across multiple tables without changing collision behavior.
- **Memory planning & `-fpmem`**: Java treats `-fpbits` and `-fpmem` as orthogonal. The configured ratio/absolute byte target is computed once (`FPSetConfiguration.getMemoryInBytes` via `TLCRuntime.getFPMemSize`) and `MultiFPSetConfiguration` divides it evenly across the child sets. Our Rust implementation will follow the same budgeting so existing sizing heuristics stay correct and the toolbox guidance (“set -fpmem to 0.5 when using fpbits=4”) remains valid.
- **Distributed & recovery flows**: Distributed TLC forwards the chosen `fpBits` to remote workers through `FPSetConfiguration` (`TLCApp` builds the same config for both server and clients, `TLCServer#getFPSetManager` → `FPSetFactory.getFPSet`, and workers fetch the bit mask through the RMI manager). Checkpoints persist the `FPSetConfiguration` so resumes keep the same sharding. Rust’s manifest and distributed control plane will serialize `fp_bits` alongside the polynomial to guarantee restarts and workers operate over identical partitions.
- **Disk/Off-heap specifics**: Disk-backed fingerprints (`MSBDiskFPSet`) rely on the MSBs to maintain bucket locality; they assume `fpBits > 0` and compute the index shift as `(32 - fpBits) - (logMaxMemCnt - LogMaxLoad)` (`MSBDiskFPSet.java:36-58`). Off-heap sets build specialized indexers keyed off `fpBits` as well (`OffHeapDiskFPSet.java:151-158`). We will port these calculations, including the two indexer variants, so large runs continue to enjoy sequential disk access and reduced collision rates.
- **Testing strategy**: Legacy has regression suites such as `MultiFPSetTest` and integration coverage inside the distributed worker tests that expect uniform distribution of fingerprints across shards. Rust parity will include unit tests that hash representative traces with varying `fpBits`, verifying the shard selection matches Java (`fp >>> (64 - bits)`) and that `fpBits=0` collapses to a single shard for in-memory sets while remaining ≥1 for disk-backed ones. End-to-end resume tests will assert the serialized manifest keeps `fp_bits` stable.

## Fingerprint Memory Parity Notes (`-fpmem`)

- **CLI parsing & diagnostics**: `tlatools/org.lamport.tlatools/src/tlc2/TLC.java:1007-1038` reads `-fpmem num`, accepts non-negative inputs, and reuses `EC.WRONG_COMMANDLINE_PARAMS_TLC` for both “missing argument” and “positive integer or fraction required” failures; the distributed launcher mirrors the same logic (`tlc2/tool/distributed/TLCApp.java:452-487`). Rust’s CLI will replicate these branches so Toolbox automation still recognises the message catalog.
- **Ratio vs absolute inputs**: Values in `[0,1]` are treated as fractions of the JVM heap (`fpSetConfiguration.setRatio`), while numbers > 1 request an absolute byte budget. Absolute inputs trigger the legacy deprecation warning (`ToolIO.out.println` in both CLI paths) and flip `setMemory` plus `setRatio(1.0)` so the full absolute allocation is reserved. The Rust implementation will keep the warning text verbatim and honour both modes for compatibility.
- **Default sizing & lower/upper bounds**: `FPSetConfiguration` defaults to a 0.25 ratio (25 % of `Runtime.maxMemory()`). `TLCRuntime.getFPMemSize` applies the same heuristics regardless of input source: it enforces a floor of `TLCRuntime.MinFpMemSize` (20 × 2¹⁹ ≈ 10 MB) and a ceiling of 75 % of the heap (`maxMemory - maxMemory/4`). We will port these guards exactly so low ratios (e.g., 0.01) still give TLC enough space while oversized requests never starve the evaluator.
- **Off-heap implementations**: When the selected `FPSet` allocates off-heap (e.g., `OffHeapDiskFPSet`), Java ignores the ratio and consumes the entire non-heap pool reported by `TLCRuntime.getNonHeapPhysicalMemory()` (`FPSetConfiguration.getMemoryInBytes`). Rust’s storage layer will inspect the backend the same way: if the implementation lives off-heap we dedicate the full configured direct-memory budget and document that ratios are advisory-only in that mode.
- **Distribution across shards**: For `MultiFPSet`, `MultiFPSetConfiguration#getMemoryInBytes` divides the computed byte budget evenly across `2^fpBits` child sets. Our port keeps the per-shard division so existing tuning—choosing `-fpbits` and `-fpmem` together—produces identical table sizes and avoids regressions in collision rates.
- **Distributed & resume parity**: The distributed server passes the configured ratio/memory to workers through serialized `FPSetConfiguration` instances (`FPSetManager` construction); checkpoints persist the same structure and `TLCRuntime` recomputes the absolute byte target on restore. The Rust runtime will encode both the input value (ratio vs absolute) and the resolved byte budget in the manifest so restarts and remote workers replay the identical sizing.
- **VM flag recommendations**: Legacy tooling surfaces JVM flag guidance via `FPSetFactory.getVMArguments` if explicit FPSet implementations are selected. We’ll preserve that helper (or equivalent documentation) so operators know to adjust `-Xmx` or `-XX:MaxDirectMemorySize` alongside `-fpmem` for large models.
- **Testing strategy**: Unit tests will cover representative inputs—fractions (0, 0.25, 0.9), absolute bytes (16 MB, > heap), and invalid negatives—checking the resulting byte count matches Java for both heap and off-heap FPSets. Integration tests will exercise distributed runs to ensure workers receive identical budgets, and resume tests will confirm checkpointed runs honour the stored memory ratio.

## Fingerprint Storage Parity Notes

- **Factory selection & overrides**: `FPSetFactory.getFPSet(FPSetConfiguration)` checks `fpBits > 0` to decide whether to wrap the backend in `MultiFPSet`. `FPSetConfiguration.getImplementation` reads the `FPSet.impl` system property (`FPSetFactory.IMPL_PROPERTY`), and unsupported classes (for example off-heap sets on x86) trigger `EC.TLC_FEATURE_UNSUPPORTED` warnings before falling back to the default `MSBDiskFPSet`. The Rust planner will mirror this decision tree so Toolbox launches and distributed servers continue to honour explicit overrides without surprising fallbacks.
- **Default disk pipeline**: `MSBDiskFPSet` extends `HeapBasedDiskFPSet`, buffering fingerprints in a striped hash table (`long[][] tbl` guarded by `Striped` RW locks) until `maxTblCnt` is reached. Flushes sort the buckets, set the `MARK_FLUSHED` bit, and append big-endian 64-bit values to `<metadir>/<spec>.fp`, maintaining a sparse index for binary search. The Rust disk backend will use the same MSB sentinel, bucket growth policy (`BucketSizeIncrement`), and flush ordering so collision behaviour and disk locality stay identical.
- **In-memory variants**: `MemFPSet`, `MemFPSet1`, and `MemFPSet2` provide pure-heap open-addressed tables with 2-bit occupancy flags and checkpoint writers that emit `<spec>.fp.chkpt` files. They are selected explicitly via `FPSet.impl` (or in DFID’s `MemFPIntSet` case) and assert using `EC.TLC_FP_NOT_IN_SET` when reloading checkpoints. We will ship Rust in-memory stores that retain the same probing sequence, checkpoint encoding, and assertion surfaces so existing “memory only” deployments continue to work.
- **Off-heap backends**: `OffHeapDiskFPSet` allocates bucket arrays in direct byte buffers, is disabled on 32-bit platforms (`FPSetFactory.supports32Bits`), and consumes the full `TLCRuntime.getNonHeapPhysicalMemory()` budget. Our Rust implementation will provide an mmap/direct-memory variant behind the same architecture guard and persist the resolved non-heap budget in the run manifest, emitting the legacy warning if the environment cannot satisfy the allocation.
- **Sharding & nested sets**: When `fpBits > 0`, `MultiFPSet` instantiates `2^fpBits` child FPSets via `MultiFPSetConfiguration`, suffixing filenames with `_<index>` during `init`. It routes every `put`/`contains` by shifting the fingerprint (`fp >>> (64 - fpBits)`). The Rust sharded store will keep this suffixing scheme and routing logic so checkpoint layouts (`states/spec.fp_3.chkpt`) and distributed reassignments remain script-compatible.
- **Checkpoint lifecycle & recovery**: `DiskFPSet.beginChkpt` forces a flush and copies `<spec>.fp` to `<spec>.fp.tmp`; `commitChkpt` renames the temp file to `.fp.chkpt`, and `recover` streams the checkpoint back into the live `.fp` while rebuilding the sparse index and resetting per-worker `BufferedRandomAccessFile` handles. Rust TLC will reproduce the same filenames, rename semantics, MSB clearing rules, and per-worker reader pool so resumes, `-cleanup`, and distributed restarts produce byte-for-byte compatible artifacts.
- **Distributed coordination**: `FPSetManager` serializes the resolved `FPSetConfiguration`, assigns remote FPSets (`FPSetRMI`) to workers, and reassigns shards on failure. It assumes identical backend behaviour across server and clients. The Rust distributed control plane will broadcast a `FingerprintStoreConfig` (backend kind, polynomial, fp_bits, byte budget) and validate worker acknowledgements, preserving `EC.TLC_FP_COMPLETED`/`EC.TLC_FP_NOT_IN_SET` outputs when shards close or recover.
- **Diagnostics & observability**: Legacy storage emits `EC.TLC_FP_COMPLETED` on clean shutdown, `EC.TLC_FP_VALUE_ALREADY_ON_DISK` when merge detects duplicates, and exposes JMX counters via `DiskFPSetMXWrapper` (flush time, disk writes, bucket occupancy). We will surface the same message codes and metrics, map them into the tool-mode catalog (`@!@!@` framing), and ensure `fingerprint` telemetry (selected polynomial, fp_bits, shards, memory) continues to appear in startup/summary banners.
- **Implementation plan**: Introduce a `fingerprint::store::Store` trait with concrete `DiskStore`, `OffHeapDiskStore`, `InMemoryStore`, and `ShardedStore` implementations. `DiskStore` keeps a striped table sized from the resolved budget, tags flushed entries with the MSB sentinel, writes sorted slabs to a single big-endian file, and builds the same sparse index layout. `OffHeapDiskStore` backs the table with arenas/mmap sized from direct memory. `ShardedStore` wraps multiple stores and routes via the MSB mask. All stores share a manifest encoder that records backend kind, polynomial index, fp_bits, memory inputs, and resolved byte count for resumes.
- **Testing**: Parity tests will cross-run Java and Rust TLC over canned models to compare generated `.fp` and `.fp.chkpt` files byte-for-byte (single disk, multi-set, off-heap, in-memory). Additional property tests will randomize insert/duplicate workloads to verify `MARK_FLUSHED` semantics and collision handling, and distributed simulations will exercise shard reassignment plus manifest propagation.

Our Rust design will mirror these call-site choices so ad-hoc tooling sees identical file formats.
- **Resume compatibility**: Because the checkpoint readers look at `TLCGlobals.useGZIP` when opening streams (`new ValueInputStream(filename)`), users must supply `-gzip` on resumes or distributed workers if the checkpoint was written with compression. Rust will enforce the same contract and warn when the detected manifest indicates gzip but the flag is missing, guiding users to re-run with the right toggle.
- **I/O stack parity**: Compression happens through the same buffering path (`util.FileUtil.newBdFIS/newBdFOS`), so we need faithful ports of buffering order, flush semantics, and error messages (`EC.SYSTEM_ERROR_READING_STATES`). We’ll validate by round-tripping sample states and ensuring byte-for-byte equality with the Java encoding (after decompression).
- **Testing**: Integration tests will cover both compressed and uncompressed runs: write a state queue, checkpoint, recover, and resume. File extension and size heuristics (compressed files typically end in `.d1`, `.queue.chkpt`) should match legacy naming. Additional tests will confirm distributed workers honour the flag and that manifest metadata records whether compression was used.

## Randomization Parity Notes

- **Seed negotiation & CLI surface**: The CLI stores the `-seed` argument (or samples `rng.nextLong()` when omitted) and applies the optional `-aril` skip before handing the generator to simulation or model checking (`tlatools/org.lamport.tlatools/src/tlc2/TLC.java:1248-1295`). Rust TLC will mirror the same handshake, including legacy parse errors and ensuring the banner prints the seed we persist for replay.
- **Model checking enumerations**: Immediately after seeding, TLC calls `RandomEnumerableValues.setSeed(seed)` so `RandomElement` and `Randomization` operators evaluate deterministically during constant, init, and next-state evaluation (`tlatools/org.lamport.tlatools/src/tlc2/value/RandomEnumerableValues.java:47-104`). The Rust engine will seed the equivalent thread-local RNG before elaboration and carry the value through checkpoints/resume.
- **Per-worker determinism**: `RandomEnumerableValues` keeps a worker-local RNG that, in model checking, XORs the predecessor fingerprint with the run seed via `TLCStateRandom` to recreate successor choices during trace replay (`tlatools/org.lamport.tlatools/src/tlc2/value/RandomEnumerableValues.java:124-170`). Combined with `WorkerValue.demux` resetting the seed when cloning mutable constants (`tlatools/org.lamport.tlatools/src/tlc2/tool/impl/WorkerValue.java:123-152`), this guarantees multi-worker runs evaluate probabilistic operators consistently. We will port the fingerprint XOR, one-time initialization guard, and demux/mux reset semantics so distributed and resumed runs stay reproducible.
- **Trace replay semantics**: When reconstructing an error trace, TLC takes a snapshot via `RandomEnumerableValues.reset()` and warns that repeated replays of random specs fail in `-continue` mode (`tlatools/org.lamport.tlatools/src/tlc2/tool/TLCTrace.java:272-318`, `tlatools/org.lamport.tlatools/src/tlc2/tool/ConcurrentTLCTrace.java:102-156`). Rust TLC will offer the same snapshot/restore behavior and document the same limitation to keep Toolbox expectations intact.
- **Simulation integration**: `Simulator` passes the shared `RandomGenerator` to each `SimulationWorker`, deriving per-worker seeds with `rng.nextLong()` and writing exported traces, DOT graphs, and coverage summaries while reporting the seed/aril pair (`tlatools/org.lamport.tlatools/src/tlc2/tool/Simulator.java:120-345`, `tlatools/org.lamport.tlatools/src/tlc2/tool/Simulator.java:571-912`, `tlatools/org.lamport.tlatools/src/tlc2/tool/SimulationWorker.java:433-707`, `tlatools/org.lamport.tlatools/src/tlc2/output/MP.java:1070-1150`). We will reuse the same 48-bit LCG, worker derivation order, and telemetry fields so deterministic simulations remain reproducible.
- **Randomization module & RandomElement**: Operators in `tlc2/module/TLC.java` and `tlc2/module/Randomization.java` rely on `EnumerableValue` helpers that draw indices via `RandomGenerator.nextPrime` and tuned LCG parameters to approximate uniform subsets (`tlatools/org.lamport.tlatools/src/tlc2/module/TLC.java:372-427`, `tlatools/org.lamport.tlatools/src/tlc2/module/Randomization.java:38-152`, `tlatools/org.lamport.tlatools/src/tlc2/value/impl/EnumerableValue.java:148-216`). The Rust value layer will port those algorithms, including the bias mitigation comments and validation errors, to keep probabilistic specs behaving identically.
- **Observability & config exposure**: Startup banners embed the active seed/fingerprint combo, simulation summaries print seed/aril, and `Simulator#createConfig` surfaces both to `TLCGet("config")` consumers (`tlatools/org.lamport.tlatools/src/tlc2/output/MP.java:1047-1150`, `tlatools/org.lamport.tlatools/src/tlc2/tool/Simulator.java:571-912`). Our status emitter will preserve the same message codes and field ordering for Toolbox and scripting parity.
- **Parity testing**: Add regressions that diff Java and Rust outputs for seeds/arils across BFS, DFID, and simulation runs; verify `RandomElement`/`RandomSubset` sequences across workers and restarts; lock down trace reconstruction for probabilistic specs; and assert that exported traces, DOT graphs, and progress telemetry remain byte-for-byte identical under fixed seeds.

## Checkpointing & Recovery Parity Notes

- **Meta directory selection & naming**: `TLC.java:1173-1189` funnels every run through `FileUtil.makeMetaDir`, which either reuses the `-recover` path (trailing separator appended during CLI parsing in `TLC.java:891-899`) or creates a new `states/<yy-MM-dd-HH-mm-ss.SSS>` directory beneath the spec root or `-metadir` override. `FileUtil.makeMetaDir` (`util/FileUtil.java:232-304`) relies on `Files#createDirectory` for atomic creation and exposes a system property to toggle millisecond precision; the Rust CLI will keep the same defaults, honor `TLCGlobals.metaDir`, and ensure the generated path is identical so shell scripts that parse timestamps keep working.
- **Checkpoint transaction semantics**: `ModelChecker.checkpoint` (`tlc2/tool/ModelChecker.java:718-760`) suspends the state queue, flushes the worker traces (`ConcurrentTLCTrace.beginChkpt`), fingerprint store (`FPSet.beginChkpt`), unique-string table (`UniqueString.internTbl.beginChkpt`), and liveness graphs (`LiveCheck.beginChkpt`) before committing each component via `.commitChkpt()` which performs the legacy `*.tmp → *.chkpt` rename. We will preserve this component order, resume signal (`stateQueue.resumeAll()`), and reuse the legacy `EC.TLC_CHECKPOINT_START/END` messages so Toolbox and scripts observe identical progress.
- **Artifact layout & filenames**: Workers write `<metadir>/<spec>-<workerId>.trace` logs plus `.tmp/.chkpt` companions (`TLCTrace.java:403-458`), the queue persists `queue.tmp/queue.chkpt` alongside numbered pool segments (`DiskStateQueue.java:69-207`), fingerprints live in `<spec>.fp`, `<spec>.fp.tmp`, `<spec>.fp.chkpt` (`DiskFPSet.java:216-737`), and unique strings store `vars.tmp/vars.chkpt` (`util/InternTable.java:118-166`). Liveness graphs save into per-checker subdirectories under the same `metadir` (`tlc2/tool/liveness/AbstractDiskGraph.java:520-606`). Distributed TLC reuses the same naming while `FPSetManager` fans out checkpoints to remote shards in parallel (`tlc2/tool/distributed/fp/FPSetManager.java:543-620`). The Rust runtime will emit byte-for-byte compatible files at those exact paths so `-recover` continues to work across implementations.
- **Frequency & forcing logic**: `TLCGlobals.chkptDuration` defaults to `(30 * 60 * 1000) + 42` ms, serving as a sentinel to detect user overrides (`TLCGlobals.chkptExplicitlyEnabled()`); `TLCGlobals.doCheckPoint()` also honors the system-property `forceChkpt` toggle and treats `0` as “disabled”. Our scheduler keeps this contract, interpreting the `-checkpoint minutes` flag identically, preserving the jitter introduced by `progressInterval`, and exposing the same JMX/system-property escape hatches for cloud supervisors.
- **Recovery workflow**: During startup `TLC` reloads the unique-string table when `-recover` is specified (`TLC.java:1252-1260`), and `ModelChecker.recover` (`tlc2/tool/ModelChecker.java:794-829`) reinstates the trace, queue, and fingerprint set before replaying initial states to rebuild liveness structures (fix for GH-22). It emits `EC.TLC_CHECKPOINT_RECOVER_START/END` with fingerprint and queue sizes, then resumes exploration. Rust TLC will follow the same sequence, including UniqueString hydration, liveness re-seeding, and message catalog usage, while tolerating both Java- and Rust-produced checkpoint layouts.
- **Cleanup, veto, and manifesting**: `ModelChecker.cleanup` (`tlc2/tool/ModelChecker.java:830-868`) takes a final snapshot when checkpoints were explicitly enabled and the run aborted (error or time bound) before optionally deleting the metadir unless vetoed by `-cleanup`/`VETO_CLEANUP`. The rewrite preserves the same heuristics and adds an _additional_ `checkpoint.manifest.json` that records the spec digest, config fingerprint, worker count, and fp parameters. Loading a legacy checkpoint simply treats the manifest as optional; when present the digest must match the current module hash before resuming, matching user expectations about “same spec or fail”.
- **Distributed parity**: `TLCServer.checkpoint` (`tlc2/tool/distributed/TLCServer.java:333-371`) suspends remote workers, checkpoints the shared queue/trace locally, and asks each `FPSetRMI` shard to flush/rename its data. Recovery mirrors this via `fpSetManager.recover`. The Rust distributed coordinator will provide the same RPC surface and staging semantics so current Toolbox/cluster orchestration scripts behave unchanged.
- **Parity testing**: We will create integration suites that (a) run Java TLC to produce checkpoints and ensure Rust can resume them, (b) run Rust, kill mid-run, and have Java resume, (c) simulate crashes between `.tmp` and `.chkpt` renames to confirm durability, and (d) exercise distributed checkpoints with multiple shards. These tests guard both the on-disk format and the scheduling decisions above.

## Coverage Reporting Parity Notes

- **CLI parsing & scheduling**: `-coverage minutes` is parsed in `tlatools/org.lamport.tlatools/src/tlc2/TLC.java:740-766`, storing the interval (minutes→ms) in `TLCGlobals.coverageInterval` while rejecting negatives with the legacy `Error: expect a nonnegative integer for -coverage option.` diagnostic. When enabled, `AbstractChecker.runTLCContinueDoing` and `DFIDModelChecker` derive a coverage countdown from `coverageInterval / progressInterval` so the periodic worker prints coverage payloads and then sleeps for `progressInterval`; simulation piggybacks on the same cadence (`Simulator.java:602-669`). Rust’s CLI will match the minutes→ms conversion, guard rails, and scheduling so runs emit at identical wall-clock intervals.
- **Data collection graph**: Coverage instrumentation is wired by `CostModelCreator.create` (invoked during checker construction and simulator startup) which spawns per-action `CostModel` trees and distinct-value counters for each `VARIABLES` declaration (`CountDistinct.SyncedHyperLogLog`). Legacy TLC relies on `Tool` to increment model counters while evaluating expressions; CostModel children reflect `OpApplNode` structure so leaf coverage matches source locations (see `ActionWrapper`, `OpApplNodeWrapper`). The Rust evaluator will build an equivalent forest—one tree per action/operator—so every evaluation increments the same primary/secondary counters (generated vs. distinct) and cost accumulators, including constraint/implied action wiring inserted by `SpecProcessor`.
- **Message catalog parity**: Coverage output is streamed entirely through the `EC.TLC_COVERAGE_*` codes (`MP.java:1186-1217`). Runs start with `TLC_COVERAGE_START`, print `<var>` summaries (`TLC_COVERAGE_VAR`), action summaries (`INIT/NEXT/CONSTRAINT/PROPERTY`), nested expression counts (`VALUE`, `VALUE_COST` for allocations), optional mismatches (`TLC_COVERAGE_MISMATCH`), and conclude with `TLC_COVERAGE_END` or `…_END_OVERHEAD` if runtime exceeds five minutes (`CostModelCreator.report`). Rust’s emitter will reuse these message identifiers, field order, and indentation via `TLCGlobals.coverageIndent` so Toolbox parsing and docs/module-coverage-statistics.md examples stay byte-for-byte compatible.
- **TLCGet integration**: `TLCGet("coverage")` returns structured records built in `tlc2/module/TLCGetSet.java:500-545`, exposing generated/distinct counts for actions and variable coverage. The Rust module shim will populate the same record layout (fields `coverage`, `generated`, `distinct`, `count`) using the shared coverage tables so specs that introspect coverage—or the Toolbox—see identical data.
- **Advanced toggles & scope**: Java supports system property overrides (`TLCGlobals.Coverage` bitmask) that selectively enable action/variable coverage even when the CLI flag is absent, and collapses identical action instances when symmetry or parameterized actions share locations (`CostModelCreator.report`). The Rust runtime preserves these toggles, the location-based ordering, and the de-duplication rules (built on per-location `CostModel` equality) to avoid regressions in scripts that rely on the subtle ordering of coverage lines.
- **Distribution & simulation**: Distributed TLC gathers coverage on the server (workers forward stats through CostModel instances) and writes reports from the coordinator, while simulation mode prints the same payload at completion (`Simulator#printSummary`). Rust’s distributed coordinator and simulator will reuse the shared coverage reporter so parity holds regardless of run mode.
- **Parity testing**: Integration suites will execute representative specs (safety, liveness, implied constraints, symmetry, PlusCal translations) under Java and Rust, diff the streamed `TLC_COVERAGE_*` sequences, and compare `TLCGet("coverage")` records. Additional stress tests will ensure allocation-cost columns, distinct-variable counters, and the overhead warning trigger at the same elapsed time.

## Spec Bundle Parity Notes

- **Legacy bundle layout**: Toolbox/cloud jobs repackage `tla2tools.jar` and drop model artifacts under `/model/`—at minimum `MC.tla`, often `MC.cfg`, all dependent `.tla` modules, plus optional `generated.properties` used to seed JVM system properties (mail targets, cloud metadata). TLC auto-detects this when the positional `SPEC` is omitted, toggles `Tool` mode, disables checkpoints, and switches the resolver to `InJarFilenameToStream` so parser/evaluator reads from the jar before falling back to the filesystem or standard library.
- **Rust parity plan**: `SpecSource::Archive` (used by CLI + distributed entry points) opens `.jar`/`.zip` archives via `zip` crate, filters contents under `/model/`, validates that `MC.tla` exists, and extracts all `/model/*.tla`/`*.cfg` (plus `generated.properties`) into a dedicated temp directory. That directory is placed at the front of the module search path, mirroring legacy resolver ordering, while standard modules remain untouched. `generated.properties` is parsed into a structured map; consumers can ignore it by default (MailSender retirement) but tooling has the metadata if reintroduced.
- **Invocation flow**: `tlc` without a positional spec attempts to load an embedded bundle (for future self-contained artifacts). Providing a `.jar`/`.zip` path binds `SpecSource::Archive`; other inputs are treated as filesystem modules. Optional `--spec-root` flag defaults to `/model/` but permits alternative roots for migration/experiments. `SpecSource` is shared with `tlc server`/resumption so distributed/cloud workflows keep a single artifact story.
- **Risk & follow-up**: Implementation requires bundler CLI tooling (e.g., `tlc bundle create`) and regression tests that diff extracted archives against known-good legacy snapshots. Track these in the tooling epic; resolver parity itself is now designed.
